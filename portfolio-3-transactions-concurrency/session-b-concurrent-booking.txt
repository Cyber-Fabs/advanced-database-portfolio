-- CareBridge Specialist Clinic: relational schema (PostgreSQL)

DROP TABLE IF EXISTS payments, invoices, lab_requests, lab_tests, prescription_items,
  prescriptions, medications, consultations, appointments, patients, doctors, departments CASCADE;

CREATE TABLE departments (
  department_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name          VARCHAR(100) NOT NULL UNIQUE,
  location      VARCHAR(100)
);

CREATE TABLE doctors (
  doctor_id     INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  first_name    VARCHAR(50) NOT NULL,
  last_name     VARCHAR(50) NOT NULL,
  specialty     VARCHAR(100),
  phone         VARCHAR(20) UNIQUE,
  department_id INT NOT NULL REFERENCES departments(department_id) ON DELETE RESTRICT
);

CREATE TABLE patients (
  patient_id    INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  first_name    VARCHAR(50) NOT NULL,
  last_name     VARCHAR(50) NOT NULL,
  date_of_birth DATE NOT NULL CHECK (date_of_birth > DATE '1900-01-01'),
  gender        VARCHAR(10) CHECK (gender IN ('Male', 'Female')),
  phone         VARCHAR(20) UNIQUE,
  blood_group   VARCHAR(3) CHECK (blood_group IN ('A+','A-','B+','B-','AB+','AB-','O+','O-'))
);

CREATE TABLE appointments (
  appointment_id   INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  patient_id       INT NOT NULL REFERENCES patients(patient_id) ON DELETE RESTRICT,
  doctor_id        INT NOT NULL REFERENCES doctors(doctor_id) ON DELETE RESTRICT,
  appointment_date DATE NOT NULL,
  appointment_time TIME NOT NULL,
  status           VARCHAR(20) NOT NULL DEFAULT 'Scheduled'
                   CHECK (status IN ('Scheduled', 'Completed', 'Cancelled', 'No-show')),
  UNIQUE (doctor_id, appointment_date, appointment_time)
);

CREATE TABLE consultations (
  consultation_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  appointment_id  INT NOT NULL UNIQUE REFERENCES appointments(appointment_id) ON DELETE CASCADE,
  symptoms        TEXT,
  diagnosis       TEXT
);

CREATE TABLE medications (
  medication_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name          VARCHAR(100) NOT NULL UNIQUE,
  unit_price    NUMERIC(10,2) NOT NULL CHECK (unit_price >= 0)
);

CREATE TABLE prescriptions (
  prescription_id INT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  consultation_id INT NOT NULL REFERENCES consultations(consultation_id) ON DELETE CASCADE,
  date_issued     DATE NOT NULL DEFAULT CURRENT_DATE
);

CREATE TABLE prescription_items (
  prescription_id INT NOT NULL REFERENCES prescriptions(prescription_id) ON DELETE CASCADE,
  medication_id   INT NOT NULL REFERENCES medications(medication_id) ON DELETE RESTRICT,
  dosage          VARCHAR(100) NOT NULL,
  quantity        INT NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (prescription_id, medication_id)
);

# Portfolio 1: Database Design and Modelling

## Case study
CareBridge Specialist Clinic, Abuja (simulated). See [case-study.md](../case-study.md).

## Files
| File | Purpose |
|---|---|
| `carebridge-clinic-erd.png` | ER diagram (exported from dbdiagram.io) |
| `carebridge-clinic-erd.dbml` | Source code of the ER diagram |
| `carebridge-schema.sql` | PostgreSQL schema: tables, keys and constraints |
| `carebridge-sample-data.sql` | Generated sample data (5,000 patients, 20,000 appointments) |
| `screenshots/` | Evidence of the schema and data being created |

## ER diagram
![CareBridge ER diagram](carebridge-clinic-erd.png)

The design has 12 entities. Key relationships:
- One department has many doctors; one doctor has many appointments.
- One patient has many appointments and many invoices.
- One appointment has at most one consultation (one-to-one, enforced by `UNIQUE`).
- Prescriptions and medications are many-to-many, resolved by the junction table `prescription_items`.
- One consultation can have many lab requests; one invoice can have many payments (part-payments).

## Keys and constraints
| Constraint | Example | Why |
|---|---|---|
| Primary key | `patient_id` (identity) | Uniquely identifies each row |
| Composite primary key | `(prescription_id, medication_id)` | Same drug cannot appear twice on one prescription |
| Foreign key | `appointments.patient_id` | Cannot book for a patient who does not exist |
| `UNIQUE` | `(doctor_id, appointment_date, appointment_time)` | Prevents double-booking a doctor |
| `CHECK` | `blood_group IN ('A+', ...)`, `quantity > 0` | Rejects invalid values |
| `ON DELETE RESTRICT` | patients, doctors | Protects medical and billing history |
| `ON DELETE CASCADE` | consultation → prescriptions | Child records removed with their parent |

## Normalisation
The schema is normalised to **Third Normal Form (3NF)**.

**First Normal Form (1NF):** every column holds a single, atomic value and every table has a primary key. For example, a prescription's medicines are not stored as a list such as "Paracetamol, Amoxicillin" in one column; each medicine is a separate row in `prescription_items`.

**Second Normal Form (2NF):** no non-key column depends on only part of a composite key. The only composite key is `(prescription_id, medication_id)`. `dosage` and `quantity` depend on both parts, while the medicine's `name` and `unit_price` depend only on `medication_id`, so they are stored in `medications`, not repeated in every prescription item.

**Third Normal Form (3NF):** no non-key column depends on another non-key column. A doctor's department name is stored once in `departments`, not in `doctors`, because it depends on `department_id` rather than on the doctor. Likewise, patient details are not repeated in `appointments`, and test prices live in `lab_tests`.

**Deliberate trade-off:** `invoices.total_amount` could be calculated from consultation, medication and test charges. It is stored to keep a fixed record of what was billed at that time and to avoid recalculating totals for every report.

| Query | Business question |

Dataset: 5,000 patients and 20,000 appointments (January to early May 2025), generated synthetically. May revenue in Q5 is lower because only the first days of May are covered.

## Indexes added
| Index | Columns | Reason |
|---|---|---|
| `idx_appointments_patient_id` | `appointments(patient_id)` | PostgreSQL does not index foreign keys automatically |
| `idx_patients_last_first_name` | `patients(last_name, first_name)` | Supports name searches at the front desk |
| `idx_invoices_unpaid_amount` | `invoices(total_amount DESC) WHERE status = 'Unpaid'` | Partial index: stores only unpaid invoices, pre-sorted by amount |

## Results
| Query | Before | After | Plan change |
|---|---|---|---|
| Q1 Patient history | 1.463 ms | 0.144 ms | Seq Scan on 20,000 appointments → index lookup (about 10× faster) |
| Q2 Doctor schedule | 0.046 ms | 0.041 ms | No change: already uses the index created by the `UNIQUE` constraint |
| Q3 Patient by name | 0.085 ms | 0.061 ms | Small gain: `LIMIT 10` let the Seq Scan stop after about 775 rows |
| Q6 Unpaid invoices | 3.240 ms | 0.114 ms | Seq Scan, filter and sort of 13,469 invoices → reads top 10 from the partial index (about 28× faster) |

## Performance analysis
The largest gains came where a query filtered a large table on a column with no index. Before indexing, Q1 read all 20,000 appointments to find one patient's visits. After indexing, PostgreSQL went straight to the matching rows.

Q6 improved most because the partial index already holds only unpaid invoices in descending amount order. PostgreSQL reads the first ten entries instead of filtering 10,793 rows and sorting the remaining 2,676.

Q2 shows that constraints also create indexes. The `UNIQUE (doctor_id, appointment_date, appointment_time)` rule that prevents double-booking also makes schedule lookups fast.

Q3 shows that an index does not always produce a large gain. Because the query stops after ten matches, the sequential scan finished early. The index matters more for rare surnames, where a full scan of all patients would otherwise be needed.

## Trade-offs and limitations
- Every index uses extra storage (see `index-sizes.txt`) and slows down inserts and updates, because the index must be updated too. Indexes should only be added for frequent queries.
- Timings are from single runs on a small dataset held in memory, so they vary slightly between runs. The plan changes (Seq Scan to index scan) are more reliable evidence than the exact milliseconds.
EOF
